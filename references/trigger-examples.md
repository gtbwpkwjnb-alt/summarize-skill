# 触发方式与输出示例

## 触发规则

**唯一触发词**：`总结` 或 `summarize`，且必须作为独立词单独发送。

| 会触发 | 不会触发 |
|-----------|-------------|
| `总结`（单独发送） | "总结一下今天的工作"（在句中） |
| `summarize`（单独发送） | "帮我总结一下进度"（在句中） |
| `总结 统计`（独立词+参数） | 会话达到任意阈值（无自动提醒） |

> 无自动提醒、无定时触发、无其它激活路径。仅独立词触发。

## 输出示例（L0 正常，简单会话）

适用于 <10 轮且 ≤2 文件的简单场景：

```总结报告
## MyProject — 完成配置文件修复，服务恢复正常

### 目标
- **主目标**: 修复数据库连接配置
- **次目标**: 验证连接池参数

### 进度
- 完成: 定位错误配置 · 修正连接串 · 验证连接
- 数据: ~5 轮 · 2 文件 · 估算 6K→0.5K

### 文件变更
| 动作 | 文件 | 原因 |
|:----:|------|------|
| M | `config/database.yml` | 修复连接串超时参数 |
| M | `.env.example` | 同步更新示例文件 |

### 决策
**#1 连接池大小改为 10**
- 结论: 固定连接池为 10
- 原因: 默认 5 不足，20 超数据库限额
- 被否: 动态调整方案（过于复杂）

### 下一步
1. 部署配置到生产环境
2. 监控连接池使用率

### 凭证
- 归档: `$HARVEST_BASE/MyProject/sess_abc.md`
- 版本: v8.2
```

## 输出示例（L0 正常，复杂会话）

适用于 >30 轮或 >8 文件的复杂场景（≤80 行）：

```总结报告
## LargeProject — 完成微服务架构迁移，12 个服务改造

### 目标
- **主目标**: 微服务架构迁移
- **次目标**: 服务拆分 · 数据库分片 · API 网关

### 进度
- 完成: 服务 A/B/C 拆分 · 数据库分片方案 · API 网关搭建
- 进行: 服务 D (70%) · 服务 E (40%)
- 阻塞: 服务 F 依赖第三方 SDK 未更新
- 数据: ~120 轮 · 25 文件 · 估算 120K→8K

### 文件变更
| 动作 | 文件 | 原因 |
|:----:|------|------|
| M | `services/auth/main.go` | JWT 签发重构 |
| M | `services/order/handler.go` | 分片键接入 |
| A | `api-gateway/routes.go` | 新网关入口 |
| A | `db/shard-config.yaml` | 分片配置 |
| D | `monolith/legacy.go` | 废弃单体代码 |

### 决策
**#1 分片键选用 user_id**
- 结论: user_id 作为主分片键
- 原因: 查询模式 90% 按用户
- 被否: order_id（数据倾斜风险）

**#2 API 网关选用 Kong**
- 结论: Kong 作为 API 网关
- 原因: 社区活跃，插件丰富
- 被否: Traefik（团队不熟）

### 错误
**ENVR** (3 次)
- 简述: 第三方 SDK 版本冲突
- 分类: 环境问题
- 规则: 用 go mod tidy 前先清理 vendor

### 知识
- 迁移顺序: 读服务 → 写服务 → 数据迁移
- Kong 性能: 1000qps 需 2 核 4G

### 下一步
1. 等待第三方 SDK 更新
2. 完成服务 E 拆分

### 凭证
- 归档: `$HARVEST_BASE/LargeProject/sess_migration.md`
- 版本: v8.2
```
