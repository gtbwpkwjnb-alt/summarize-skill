# summarize — 建议生成规则（v10.1）

根据当前总结中的证据生成可执行建议。只使用当前可见会话、工具输出和已读取文件；不要把猜测包装成诊断。

## 选择顺序

1. 先选择能解除当前阻塞或避免错误扩大的操作。
2. 再选择能消除重复问题根因的优化。
3. 最后选择能改善下一次执行方式的行为建议。
4. 证据不足时写“无法判断”，不要为了完整性编造建议。

## 信号与建议

| 信号 | 建议类型 | 最小可执行建议 | 验证 |
|---|---|---|---|
| 同一错误或失败在当前会话出现至少两次 | 优化 | 停止原路径；定位共同前提；选择一个替代方案或补充一个覆盖该前提的测试 | 下一次执行不再命中同一失败，或新增测试稳定通过 |
| 测试、构建或命令失败 | 立即行动 | 保留失败输出；定位首个可行动错误；修复后重跑同一验证 | 退出码与关键断言符合预期 |
| 完成声明缺少验证 | 行为 | 在继续或交付前补跑最小相关验证；未通过前将状态保持为“进行中” | 输出可关联的验证结果 |
| 任务受外部权限、网络或用户输入阻塞 | 立即行动 | 明确所缺内容和最小授权；等待答复前不重复同一请求 | 获得输入/授权，或改走已确认替代路径 |
| 关键决策没有理由或验收条件 | 行为 | 补充“为什么选此方案”和一个可测通过条件 | 下次交接可直接复用该决定 |
| 用户多次修正目标、范围或格式 | 优化 | 在下一次改动前列出目标、边界和验收项，等待确认 | 后续交付无需再次纠正同一约束 |
| 无异常信号 | 行为 | 按“当前应做”执行；关键完成声明前补足验证 | 下一次总结有对应验证证据 |

## 输出约束

- 使用“观察 → 影响 → 操作 → 验证”表达，不超过两行。
- 对代码级优化，只有已读取相关文件时才给出文件或函数名；否则先建议定位，不猜路径。
- 将需要用户选择、写入、外部通信或范围扩大的一步标为“需确认”。
- 不重复“下一步”中的同一句；建议应解释为什么做、如何防复发或怎样验证。
